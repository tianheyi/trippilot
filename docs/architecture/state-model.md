# 状态模型

> **状态**：本文档描述设计原则与目标形态。
> **已实现**的只有 `domain/models.py::TripRequest` 及其校验规则；槽位合并、冲突检测、Checkpoint 均**未实现**。

---

## 1. 三类状态必须分开

这是本项目最容易搞混、也最容易出事故的地方。

| | A. 旅行业务数据 | B. Agent 执行状态 | C. 外部工具结果 |
| --- | --- | --- | --- |
| **内容** | 正式保存的行程及其版本 | 对话上下文、节点进度、恢复信息 | 查询结果 + 来源 + 时间 |
| **存储** | PostgreSQL（`infrastructure/persistence/`） | LangGraph Checkpoint | 缓存（未定） |
| **权威性** | **权威**，用户可见、可导出 | 辅助，可丢弃 | 参考，会过期 |
| **生命周期** | 永久（用户删除为止） | 会话级，可设 TTL | 分钟到小时级 |
| **丢失后果** | 用户数据丢失 | 需重新说明需求，体验降级 | 重新查询 |
| **能否重放** | 不能 | 可以 | 可以 |
| **一致性要求** | 事务 + 版本号 | 最终一致即可 | 尽力而为 |

### 三条铁律

1. **Checkpoint 不是业务数据库。** 它用于恢复工作流执行，不能作为行程的唯一存储。
2. **Checkpoint 恢复不保证副作用 exactly-once。** 恢复会重放节点，因此任何写操作必须有幂等键。
3. **工具结果不是事实的永久来源。** 必须携带获取时间与有效期，过期即失效。

## 2. 旅行需求状态（槽位模型）

### 2.1 槽位定义

已实现于 `src/trippilot/domain/models.py`：

| 槽位 | 类型 | 必填 | `None` 的语义 |
| --- | --- | --- | --- |
| `origin` | `str \| None` | 否 | 用户未说出发地 |
| `destination` | `str \| None` | **是** | 用户未说目的地 |
| `start_date` | `date \| None` | **是** | 用户未说日期 |
| `end_date` | `date \| None` | 否 | 未给结束日期 |
| `days` | `int \| None` (1–30) | **是**\* | 未给天数 |
| `budget` | `Budget \| None` | 否 | 未提预算（**不是 0，也不是"免费"**） |
| `interests` | `tuple[Interest, ...]` | 否 | 空元组表示未提兴趣 |
| `travelers` | `int \| None` (1–20) | 否 | **未说人数（不是 1 人）** |
| `pace` | `Pace \| None` | 否 | 未提节奏 |
| `notes` | `str \| None` | 否 | 无备注 |

\* `days` 可由 `start_date` + `end_date` 推导满足。

### 2.2 空值语义：`None` ≠ 默认值

**这是整套状态模型最重要的一条约定。**

```
travelers=None  表示"用户没说"，不是"默认 1 人"
budget=None     表示"用户没提预算"，不是"不要钱"
interests=()    表示"用户没提兴趣"，不是"对什么都没兴趣"
```

后果：

- **系统可以用默认值继续**（例如按 1 人规划），但**必须在输出中显式说明这个假设**。
- 用于默认值的地方，不能写回 `TripRequest`——那会把"假设"污染成"事实"，后续轮次再也分不清用户到底说没说。

区分手段：`missing_slots()` 返回缺失槽位名，由调用方决定是追问还是填默认值。

### 2.3 必填槽位与优先级

`REQUIRED_SLOTS = ("destination", "start_date", "days")`

这三个缺失时**无法生成任何行程**，必须追问。其余槽位可以带默认值继续。

追问顺序按阻塞程度排序（见 `user-flows.md`），一次不超过 2 个问题。

### 2.4 已实现的校验规则

| 规则 | 行为 | 测试 |
| --- | --- | --- |
| `end_date` 不得早于 `start_date` | 抛 `ValidationError` | `TestDateRules` |
| `days` 不得与日期区间矛盾 | 抛 `ValidationError` | `TestDateRules` |
| `days` ∈ [1, 30] | 抛 `ValidationError` | `TestDateRules` |
| `budget.amount` ≥ 0，最多 2 位小数，`Decimal` 而非 `float` | 抛 `ValidationError` | `TestBudget` |
| `travelers` ∈ [1, 20] | 抛 `ValidationError` | `TestOtherFields` |
| `interests` 去重且保持首次出现顺序 | 自动处理 | `TestInterests` |
| 未知字段 | 抛 `ValidationError`（不静默丢弃） | `TestOtherFields` |

**关于冲突为什么直接抛错**：当前 `domain/` 只陈述事实、不做协商。正常流程中，澄清节点会在**校验之前**发现矛盾并询问用户，因此矛盾不应到达领域模型。领域模型抛错是**防御性兜底**，用于捕获工作流中的 bug。

## 3. 槽位增量更新（未实现）

### 设计原则

```python
# 多轮对话中，每轮只更新被明确提及的槽位
merged = current.model_copy(update={"pace": Pace.RELAXED})
```

规则：

1. **只覆盖显式提及的槽位。** 用户本轮没说 `origin`，`origin` 保持不变。
2. **不填充默认值。** 默认值只在生成行程时临时应用，不写回状态。
3. **用户显式否定 → 置回 `None`。** "预算随便"应清空 `budget`，而不是留旧值。
4. **`notes` 累积而非覆盖**（保留历史备注），但需设上限并去重。
5. **每次更新产生新版本**，便于回滚与审计。

### 为什么不用 `dict.update()`

`dict.update()` 无法区分"用户没说"和"用户说要清空"。必须用 `model_copy(update=...)` 配合**显式传入的字段集合**——只有出现在本轮解析结果中的槽位才被写入。

## 4. 冲突澄清（未实现）

### 冲突类型

| 类型 | 例子 | 检测方式 |
| --- | --- | --- |
| **内部矛盾** | `days=3` 但日期跨度 5 天 | 确定性规则（已实现于领域模型） |
| **物理不可行** | 一天排 6 个相距很远的景点 | 时间/通勤估算 |
| **约束互斥** | 预算 500 元要住 5 晚五星 | 价格区间 |
| **偏好冲突** | "不去人多的地方" + "必须去橘子洲" | 规则 + 知识 |
| **模糊歧义** | "预算 2000"（总额还是人均？） | 口径未指定即歧义 |

### 处理流程

```
检测到冲突
  │
  ├─ 1. 分类：是"用户说错了"还是"需求本身做不到"？
  │
  ├─ 2. 若可自动消解（如 days 与日期矛盾）→ 追问确认哪个为准
  │
  ├─ 3. 若不可消解（物理不可行）→ 给出 2–3 个取舍方案，让用户选
  │
  └─ 4. 绝不静默决定
```

### 反模式

| ❌ 错误做法 | 为什么错 |
| --- | --- |
| 静默砍掉一个景点 | 用户不知道，会以为系统漏了 |
| 排出物理上无法完成的行程 | 直接不可用 |
| 把超预算当作满足 | 破坏信任 |
| 把"预算 2000"擅自理解为总额 | 口径错了整份行程都错 |

## 5. Agent 执行状态与 Checkpoint（未实现）

### 需要保存的内容

| 内容 | 用途 |
| --- | --- |
| 对话历史（或摘要） | 理解后续轮次 |
| `TripRequest` 当前值 | 槽位合并的基线 |
| 当前节点与已完成节点 | 恢复执行位置 |
| 待澄清的问题 | 恢复后继续追问 |
| 中间结果（工具调用产物） | 避免重复调用 |

### 恢复语义

```
用户带 tripId 回到会话
      │
      ├─ 1. 从业务库读出行程（权威数据）
      ├─ 2. 从 Checkpoint 读执行状态（辅助）
      ├─ 3. Checkpoint 缺失/过期？
      │       └─ 是 → 仅凭行程重建上下文，功能降级但不报错
      └─ 4. 继续执行
```

### 重复执行风险与对策

恢复会重放节点。**LangGraph Checkpoint 只保证状态一致，不保证外部副作用只发生一次。**

| 风险 | 对策 |
| --- | --- |
| 重复写入行程 | 幂等键（`tripId` + `version` 作为唯一约束，冲突则跳过） |
| 重复调用付费 API | 工具结果缓存（key = 规范化入参 + 时间窗） |
| 并发修改同一行程 | 乐观锁：写入时校验 `version`，不匹配则拒绝 |
| 重复发送通知（未来） | 幂等键 + 发送记录表 |

**原则**：任何有副作用的操作，都必须能回答"这个操作执行两次会怎样"。答不上来就不许上线。

### 事务边界

- 一次行程更新 = 一个事务（行程主记录 + 条目 + 版本号），要么全成功要么全回滚。
- **外部工具调用不在事务内**——网络调用不能持有数据库事务。
- 事务内只做本地写入。

## 6. 外部工具结果状态（未实现）

### 必须携带的元数据

```python
class ToolResult[DataT](BaseModel):
    data: DataT
    source: SourceRef        # provider 名称 + 可选 URL
    fetched_at: datetime     # 获取时间（UTC）
    expires_at: datetime | None   # 有效期；None 表示不失效
    is_stale: bool = False   # 已过期但无替代数据时置 True
```

### 时效性策略

| 数据类型 | 建议有效期 | 理由 |
| --- | --- | --- |
| 天气 | 数小时 | 变化快 |
| 景点开放时间 | 数天～数周 | 变化慢但会因季节/检修调整 |
| 票价 | 数天 | 会调整 |
| 通勤时长 | 数小时（高峰期不同） | 受时段影响大 |
| 行政区划 / 城市名 | 近乎永久 | 极少变化 |

### 过期处理

```
结果过期
   ├─ 重新查询成功 → 用新数据
   ├─ 重新查询失败 → 使用旧数据 + is_stale=True + 输出中告警
   └─ 无旧数据     → 该字段标注"未知，建议出行前确认"
```

**绝不允许**：过期数据被静默当作最新数据使用，或模型自行"补上"缺失字段。

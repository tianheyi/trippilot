# 用户流程

> **状态**：本文档描述目标流程，其中标注为"未实现"的环节当前均不存在。
> 已实现的部分只有：`GET /health`、`GET /ready`、领域模型与槽位完整性规则。

## 1. 主流程：从零生成一份行程

```
用户                    前端                  API                 Agent 工作流              工具
 │                       │                    │                       │                    │
 │  自然语言描述需求       │                    │                       │                    │
 ├──────────────────────>│                    │                       │                    │
 │                       │  POST /api/v1/trips│                       │                    │
 │                       ├───────────────────>│                       │                    │
 │                       │                    │  ── 未实现 ──>          │                    │
 │                       │                    │                       │  parse_request     │
 │                       │                    │                       │  check_slots       │
 │                       │                    │                       │                    │
 │                       │                    │            ┌──────────┴──────────┐         │
 │                       │                    │            │ 槽位齐全？           │         │
 │                       │                    │            └──────────┬──────────┘         │
 │                       │                    │                否 │        │ 是             │
 │                       │                    │                   v        v                │
 │                       │                    │            生成澄清追问   gather_context    │
 │                       │  {status:           │                   │        ├───────────────>│
 │  澄清问题             │<───────────────────┤                   │        │  景点/天气/路线  │
 │<──────────────────────┤                    │                   │        │<───────────────┤
 │  回答                 │                    │                   │        v                │
 ├──────────────────────>├───────────────────>│                   │     plan_itinerary      │
 │                       │                    │                   │        │                │
 │                       │                    │                   │  校验约束（预算/时间）    │
 │                       │                    │                   │        │                │
 │                       │  {tripId, version, │<──────────────────┘        │                │
 │  行程 + 解释 + 告警      │   days[], warnings}│                                │                │
 │<──────────────────────┤                    │                       │                    │
```

### 关键设计点

- **澄清不是异常路径，而是正常工作流的一部分。** 缺槽位时返回 `status: "needs_clarification"`，不是错误。
- **`gather_context` 在 `plan_itinerary` 之前。** 先拿到事实，再排行程；不允许先排再补事实（那会诱发编造）。
- **约束校验是独立步骤。** 生成的行程必须过一遍确定性校验，不合格就带着原因重排或降级，而不是直接返回。

## 2. 澄清流程：一次只问最关键的问题

### 目标

用户说"我想去长沙玩几天"时：

| 做法 | 评价 |
| --- | --- |
| 直接生成一份假定 3 天的行程 | ❌ 猜错了要重来，浪费一轮 |
| 一次问 5 个问题（出发地/日期/天数/预算/兴趣） | ❌ 问卷感，用户流失 |
| 只问"哪天出发？"（最重要的阻塞项） | ✅ 其余可用合理默认值 |

### 判定顺序（确定性规则，不依赖 LLM）

槽位按"阻塞程度"排序，只有阻塞项才追问：

| 优先级 | 槽位 | 处理 |
| --- | --- | --- |
| 1（必须追问） | `destination` | 没有目的地无法做任何事 |
| 2（必须追问） | `start_date` | 决定天气、开放时间、节假日 |
| 3（必须追问） | `days` / `end_date` | 决定行程长度 |
| 4（可默认） | `origin` | 影响交通建议，不影响主体行程 |
| 5（可默认） | `pace` | 默认 `balanced` |
| 6（可默认） | `interests` | 不填则走通用推荐 |
| 7（可默认） | `budget` | 不填则不显示预算约束，但明确告知 |
| 8（可默认） | `travelers` | 默认 1 人，但**需在输出中说明该假设** |

**注意**：默认值不是静默填充。凡是用默认值的地方，都必须在结果里显式说明"我假设了 X"。

### 冲突澄清

用户说"长沙一天玩完岳麓山、橘子洲、省博、太平街，还要去宁乡"时：

```
检测到冲突
  └─ 类型：时间不可行（估算通勤 + 游览 ≈ 14h，超出单日可用时间）
  └─ 输出：明确指出冲突 + 给出 2–3 个取舍方案
       ├─ 方案 A：去掉宁乡，其余保留（推荐）
       ├─ 方案 B：拆成两天
       └─ 方案 C：压缩每站时长（说明会牺牲体验）
```

**不允许**：静默砍掉一个景点、或排出一份物理上无法完成的行程。

## 3. 增量修改流程

```
用户：第三天不想去博物馆了，换成室内的，预算再加 500

  │
  ├─ 1. 定位修改目标：day 3 中的 attraction 类型 item
  ├─ 2. 解析约束变更：{day3.remove: 博物馆, day3.add: 室内, budget: +500}
  ├─ 3. 确定影响范围：
  │      受影响的只有 day 3 + 预算总额
  │      day 1 / day 2 / day 4 及其余约束 → 冻结，不重算
  ├─ 4. 局部重算：只对 day 3 重新查询候选并排程
  ├─ 5. 全局校验：预算、天数、硬约束重新过一遍
  └─ 6. 版本号 +1，返回完整行程 + 变更说明
```

### 硬性要求

| 要求 | 原因 |
| --- | --- |
| 未提及的天数**逐字节不变** | 用户会立刻注意到意外变化，信任崩塌 |
| 返回中显式列出"改了什么" | 用户需要确认系统理解正确 |
| 若局部重算引发全局冲突，**明确告知** | 不允许静默放宽其他约束 |
| 版本号递增 | 支撑并发修改检测与回滚 |

## 4. 保存与恢复流程

用户中途离开，第二天回来继续。

```
第一次会话                          第二次会话
    │                                   │
    ├─ 对话上下文 ──> Agent Checkpoint   │
    ├─ 生成行程 v3 ──> 业务数据库         │
    │                                   │
    └─────────── 会话结束 ───────────────┘
                                        │
                          用户带 tripId 回来
                                        │
                                        v
                          1. 从业务库读出行程 v3（权威数据）
                          2. 从 Checkpoint 恢复对话进度（辅助上下文）
                          3. 若 Checkpoint 缺失/过期 → 仅凭行程重建上下文，功能降级但不报错
```

### 为什么必须分开存

| | 业务数据库 | Agent Checkpoint |
| --- | --- | --- |
| 存什么 | 正式行程及其版本 | 对话上下文、节点执行进度 |
| 权威性 | **权威**，用户可见 | 辅助，可丢弃 |
| 丢失后果 | 用户数据丢失 | 需要重新说明需求，体验降级但可恢复 |
| 能否重放 | 不能（有副作用） | 可以（但副作用不保证 exactly-once） |

**Checkpoint 恢复会重放节点，因此任何有副作用的操作必须靠幂等键去重，不能指望 Checkpoint 保证只执行一次。**

## 5. 错误与降级流程

### 外部工具失败

| 场景 | 处理 |
| --- | --- |
| 超时（可重试） | 指数退避重试，最多 2 次 |
| 5xx（可重试） | 同上 |
| 参数错误 / 404（不可重试） | 立即失败，不走重试 |
| 重试耗尽 | 降级：**明确告知该部分信息不可用**，行程仍生成，但相关字段标注"待确认" |

**绝不允许**：工具失败后由模型"补上"缺失的事实。

### 数据过期

```
工具返回：{ 开放时间, fetchedAt: T-8d, expiresAt: T-1d }
                              │
                              v
                        已过期 → 重新查询
                              │
                     查询失败 ├─> 标注"信息可能已变化，建议出行前确认"
                              └─> 不静默使用过期数据
```

### 配置错误

启动阶段即失败，错误信息指出具体环境变量（见 `Settings.check_startup_requirements()`）。
**不存在**"带着错误配置启动、之后在请求中才暴露"的路径。

## 6. 已实现的流程（可验证）

当前仓库中唯一可运行的流程是运维探针流程：

```
k8s / LB                      TripPilot
   │                              │
   ├─ GET /health ───────────────>│  进程存活？→ 200（不做任何 I/O）
   │<─────────────────────────────┤
   │                              │
   ├─ GET /ready ────────────────>│  检查 required 依赖
   │<─────────────────────────────┤  当前数据库为 required=false
   │     200 {dependencies:[...]} │  → 200，且如实报告 not_configured
   │                              │
   └─ 任何请求带 X-Trace-Id ──────>│  复用该 id，回写响应头，
                                  │  并写入该请求的所有日志行
```

验证方式：

```bash
make run-reload
curl -i http://127.0.0.1:8000/health
curl -i -H "X-Trace-Id: my-trace-123" http://127.0.0.1:8000/ready
```

# TripPilot 产品需求文档（PRD）

> **状态说明**：本文档描述**目标形态**。除"当前实现状态"一节所列内容外，其余能力**均未实现**。
> 请勿把本文件中的规划当作已完成能力。

---

## 1. 产品定位

TripPilot 是一个面向**中国境内旅行**的 AI 行程规划助手。

它不卖机票酒店，也不做预订。它解决的问题是：**把一段模糊的、口语化的出行意愿，变成一份可执行、可修改、能被解释的行程安排。**

### 为什么需要它

现有工具大致分两类，各有明显缺陷：

| 类型 | 代表 | 缺陷 |
| --- | --- | --- |
| 搜索引擎 / 内容社区 | 小红书、马蜂窝 | 信息正确但**不成体系**，用户要自己拼装、自己排期、自己算预算与通勤 |
| 传统行程工具 | 各类"行程单"应用 | 只是**空表格**，用户仍需自己填内容 |
| 通用聊天机器人 | 各类对话式助手 | 回答流畅但**会编造**开放时间、票价、距离；且无法增量修改，改一处要重来 |

TripPilot 的差异点在于**约束求解 + 不编造 + 可增量修改**：

1. 显式建模用户约束（预算、天数、节奏、兴趣），并检查冲突。
2. 所有事实性信息来自外部工具，附带来源与获取时间，模型不得凭记忆生成。
3. 行程是结构化数据，支持"第三天换成博物馆"这类局部修改，而不是整份重写。

### 为什么是"境内"

境内旅行有三个明确的好处，也是本项目选择它的理由：

- **信息可得**：景点、天气、交通都有相对可靠的国内数据源。
- **约束可控**：不涉及签证、汇率、语言、跨境支付等复杂变量。
- **可评测**：可以构造有明确正确答案的评测集（例如"长沙三日游"）。

## 2. 目标用户

### 主要用户：计划型自由行旅客

- 年龄 22–40，习惯用手机搜索与规划。
- 一年出行 2–5 次，多为周末短途或 3–5 天中长途。
- 有明确偏好（爱美食、爱人文、带娃、不想太累），但**懒得自己查资料排期**。
- 已在使用小红书 / 大众点评 / 高德，但不满意于"信息要自己拼"。

### 典型画像

**A. 周末短途的年轻上班族**
> 周五晚上从深圳出发，长沙玩三天，预算 2000，喜欢美食和人文景点，不想每天安排太满。

痛点：只有碎片时间做攻略，希望直接拿到可执行的安排。
核心诉求：**快**，且别太累。

**B. 带娃出行的家庭**
> 带孩子去北京，五天，孩子 6 岁，不想走太多路，要有一天去环球影城。

痛点：需要考虑体力、午休、儿童友好度，通用攻略不适用。
核心诉求：**节奏与适配**，以及明确的"哪天做什么"。

**C. 目的地已定的深度游客**
> 去成都，重点是吃，别的随便，四天。

痛点：兴趣极度集中，通用行程推荐大量无关景点。
核心诉求：**按兴趣加权**，而非平均分配。

### 次级用户

- **需要行程交付物的人**：帮家人朋友规划行程、公司团建初步方案。
- **未来**：需要行程 API 的第三方应用（本阶段不做）。

### 非目标用户（本阶段）

- 跟团游用户（不需要行程规划）。
- 商务出行（核心诉求是效率与合规，不是体验）。
- 境外旅行者（见"非目标"）。

## 3. 核心场景

### 场景 1：从零规划一次短途旅行（主场景）

用户给出自然语言描述 → 系统提取需求 → 对缺失/冲突项追问 → 查询景点与天气 → 生成行程。

**成功标准**：用户拿到行程后，不需要再打开其他 App 查"这个景点几点开门"。

### 场景 2：信息不完整时的澄清

> 用户：我想去长沙玩几天

系统需要判断：缺出发地、缺日期、缺天数。**不应该直接生成一份猜测的行程**，而应该问最有价值的那一个或两个问题（而非一次抛出五个问题）。

**成功标准**：追问轮次尽可能少，且问的是真正影响结果的问题（例如"哪天出发"比"你从哪出发"更关键）。

### 场景 3：增量修改

> 用户：第三天不想去博物馆了，换成室内的，预算再加 500

系统需要：定位到第三天 → 理解修改意图 → 只重算受影响的部分 → 保持其余安排不变。

**成功标准**：未被提及的天数**不发生任何变化**。

### 场景 4：约束冲突的识别

> 用户：长沙一天玩完岳麓山、橘子洲、湖南省博物馆、太平街，还要去趟宁乡

系统需要识别出这在时间/通勤上不可行，并**明确指出冲突在哪**，给出取舍建议，而不是假装排得下。

**成功标准**：不生成物理上无法完成的行程。

### 场景 5：行程的保存与恢复

用户中途离开，第二天回来继续修改同一份行程。
系统需要区分"正式保存的行程"与"未完成的对话进度"。

**成功标准**：恢复后上下文完整，且不会因为重放而产生重复的副作用。

## 4. MVP 范围

MVP 的目标是**证明闭环成立**，不是覆盖所有场景。

### 范围内

| 能力 | 说明 |
| --- | --- |
| 单轮需求提取 | 从一段自然语言中提取结构化需求 |
| 槽位完整性检查 | 判断哪些必填槽位缺失 |
| 澄清追问 | 针对缺失/冲突项生成追问，支持多轮 |
| 单城市行程生成 | 一个目的地城市，1–10 天 |
| 行程结构化输出 | 按天、按时间段的安排，含交通方式与耗时估算 |
| 预算与节奏约束 | 预算总额校验、每日强度符合节奏偏好 |
| 兴趣加权 | 按用户兴趣调整景点权重 |
| 增量修改 | 对已生成行程做局部修改 |
| 来源可追溯 | 每个事实性字段标注来源与获取时间 |

### 范围外（MVP 不做）

- 多城市 / 跨城联游路线优化
- 机票、火车票、酒店的**预订**（只做信息参考）
- 实时价格与余票
- 支付、发票、报销
- 社交分享、行程协作编辑
- 语音输入
- 境外旅行
- 多 Agent 协作

## 5. 用户输入与输出

### 输入

自然语言自由文本，典型长度 10–200 字。可能包含：

- 出发地 / 目的地（城市名，可能有别名："星城"→长沙）
- 时间（相对："下周五晚上"；绝对："10 月 16 日"；模糊："国庆"）
- 天数（"三天"、"玩到周日"）
- 预算（"2000 元"、"预算不多"）
- 兴趣（"喜欢美食"、"带孩子"）
- 节奏（"不想太满"、"随便逛逛"）
- 人数、同行人构成
- 硬约束（"必须去岳麓山"）
- 否定约束（"不去人多的地方"）

### 输出

结构化行程，至少包含：

```jsonc
{
  "tripId": "...",
  "version": 3,                    // 每次修改递增
  "request": { /* 最终确认的旅行需求 */ },
  "days": [
    {
      "date": "2026-10-17",
      "theme": "人文与市井",
      "items": [
        {
          "startTime": "09:00",
          "endTime": "11:30",
          "type": "attraction",     // attraction | meal | transit | rest | free
          "title": "湖南省博物馆",
          "reason": "符合你的人文兴趣，且上午人流较少",
          "cost": { "amount": "0.00", "currency": "CNY" },
          "source": {
            "provider": "mock-poi",
            "fetchedAt": "2026-10-12T02:00:00Z",
            "expiresAt": "2026-10-19T02:00:00Z"
          }
        }
      ],
      "estimatedCost": { "amount": "180.00", "currency": "CNY" },
      "pace": "relaxed"
    }
  ],
  "totalCost": { "amount": "1860.00", "currency": "CNY" },
  "warnings": [
    "10 月 18 日预报有雨，户外行程已备选室内方案"
  ],
  "unsatisfied": [
    { "constraint": "预算 2000 元", "status": "satisfied" }
  ]
}
```

设计要点：

- **每个 item 都有 `reason`**：行程要可解释，用户才知道为什么这么排。
- **每个事实性字段都有 `source`**：来源 + 获取时间 + 有效期，过期即降级。
- **`warnings` 与 `unsatisfied`**：无法满足的约束要**说出来**，而不是默默违反。
- **`version`**：支撑增量修改与并发校验。

## 6. 主要业务约束

### 6.1 事实性约束（不可协商）

1. **禁止编造**：开放时间、票价、天气、交通时长、距离一律来自工具。
2. **禁止无来源断言**：模型不能输出工具没返回的事实。不确定就标注为"未知，建议出行前确认"。
3. **来源必须可见**：用户应能知道每条信息的来源与时效。

### 6.2 时间与地理约束

4. 行程中的时间安排必须在物理上可行（含通勤时间）。
5. 同一时间段不得安排两个冲突项。
6. 每日安排需符合节奏偏好：`relaxed` 不应出现连续 12 小时高强度安排。

### 6.3 预算约束

7. 预算是有币种和口径的（总额 / 人均），二者不可混用。
8. 超预算时**必须显式告警**，不得静默超出。

### 6.4 交互约束

9. 澄清追问一次不超过 2 个问题。
10. 追问必须针对**真正影响结果**的槽位，不追问可从上下文推断的信息。
11. 增量修改不得改动用户未提及的部分。

### 6.5 数据与安全约束

12. 不记录用户隐私与完整敏感请求内容。
13. 所有重试有上限；外部调用必须有超时。
14. 有副作用的操作（未来）必须幂等。

### 6.6 质量约束

15. 关键输出必须通过 Pydantic 模型校验，模型不得绕过校验直接产出正式数据。
16. 每一次行程生成都必须可被评测用例复现（相同输入 + 相同工具数据 → 可比较的输出）。

## 7. 成功指标（待建立基线）

**当前没有任何指标基线，以下为待测量的目标，不是已达成结果。**

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 任务成功率 | 端到端完成率 | 用户给出可执行需求后，成功产出行程的比例 |
| 澄清效率 | 平均追问轮次 | 越少越好；同时看"是否问对了问题" |
| 槽位准确率 | 提取 F1 | 按槽位分别统计，日期与预算最关键 |
| 约束满足率 | 硬约束满足比例 | 预算、必去景点、天数 |
| 事实准确率 | 无来源断言数 | 目标为 0 |
| 修改保真度 | 未提及部分不变率 | 目标为 100% |
| 性能 | P95 延迟 | 生成一份 3 日行程的端到端耗时 |
| 成本 | 单次行程 Token 消耗 | 按模型分别统计 |

具体定义与测量方法见 [`docs/quality/evaluation-plan.md`](../quality/evaluation-plan.md)。

## 8. 风险与开放问题

| 风险 | 影响 | 应对方向 |
| --- | --- | --- |
| 中文相对时间解析歧义（"下周五"） | 槽位提取错误，后续全错 | 相对时间一律**回显确认**后再使用 |
| 景点数据源质量参差 | 事实错误直接摧毁信任 | 多源交叉验证 + 强制标注来源与时效 |
| 用户需求本身自相矛盾 | 无法生成行程 | 显式识别冲突并让用户取舍，不擅自决定 |
| 通勤时间估算误差 | 行程不可执行 | 采用保守估计，并在输出中标注为估算 |
| 行程修改的级联影响 | 改一处导致全天崩坏 | 明确"局部重算"边界，未提及部分不重排 |
| LLM 成本随对话轮次增长 | 单次成本失控 | 上下文摘要 + Token 预算上限 + 观测 |

**开放问题**（需要在实现前定稿）：

1. 澄清追问的触发阈值：哪些槽位缺失必须追问，哪些可以用合理默认值？
2. 行程的时间粒度：半小时还是按"上午/下午/晚上"分段？
3. 用户说"随便"时，系统应该给推荐还是继续追问？
4. 多城市联游的优先级：MVP 之后立刻做，还是等单城市稳定？
5. 前端交互形态：一次性生成完整行程，还是边问边生成？

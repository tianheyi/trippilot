# Agent 评测方案

> **状态**：**纯设计方案。当前没有任何评测实现，也没有任何测量结果。**
> 本文档中出现的所有指标名都是**待建立的定义**，不是已达成的数值。
> 唯一的已落地产物是数据格式与样例：[`evals/cases.jsonl`](../../evals/cases.jsonl)。

---

## 1. 测试与评测的区别

| | 测试（`tests/`） | 评测（`evals/`） |
| --- | --- | --- |
| 回答 | 对 / 错 | 有多好 |
| 断言 | 确定性 | 分布性、可比较 |
| 输入 | 构造的边界用例 | 贴近真实的场景集 |
| 输出 | 通过 / 失败 | 指标数值 + 失败案例清单 |
| 何时跑 | 每次提交 | 每次提示词/模型/工具变更 |

**评测不能替代测试，测试也不能替代评测。** 「槽位提取 F1 = 0.82」不能说明代码没有 bug；「78 个测试通过」也不能说明行程质量可接受。

---

## 2. 评测层次

```
L1 组件级    单个节点的输入输出        ← 最先做，最便宜，最可复现
   │         例：槽位提取、工具参数生成
   v
L2 流程级    多节点协作，含澄清回路     ← 验证状态机正确
   │         例：缺槽位 → 追问 → 补全 → 生成
   v
L3 端到端    一句话 → 完整行程         ← 验证用户价值
   │
   v
L4 回归      与基线对比，防止退化       ← 长期运行
```

**推进顺序**：L1 全部达标前不做 L3。组件级失败会污染端到端结果，让问题难以定位。

## 3. 指标体系

### 3.1 意图识别

| 指标 | 定义 |
| --- | --- |
| 意图准确率 | 正确分类的轮次 / 总轮次 |
| 混淆矩阵 | 重点关注 `new_trip` ↔ `modify_trip` ↔ `clarification_answer` 的混淆 |

**意图标签集**（草案）：

```
new_trip             发起新的行程规划
modify_trip          修改已生成的行程
clarification_answer 回答系统的追问
query_trip           询问已有行程的信息
out_of_scope         与旅行规划无关
```

**为什么混淆矩阵比准确率重要**：把 `modify_trip` 误判为 `new_trip` 会让用户丢失已有行程——代价远高于把 `out_of_scope` 误判为 `query_trip`。

### 3.2 槽位提取与增量更新

**逐槽位统计**，不只看总体：

| 槽位 | 指标 | 说明 |
| --- | --- | --- |
| `destination` | 精确匹配准确率 | 需处理别名（"星城"→长沙） |
| `start_date` | 归一化后准确率 | 相对时间（"下周五"）需先归一到绝对日期 |
| `days` | 准确率 + 与日期区间的一致性 | |
| `budget` | 金额准确率 + **口径准确率** | 总额 / 人均是独立的判定项 |
| `interests` | 集合 F1 | 多提取与漏提取分别统计 |
| `pace` | 准确率 | |
| `travelers` | 准确率 | 含"我们俩"这类隐含表达 |

**增量更新单独评测**（当前 `cases.jsonl` 中的 `slot_update` 类别）：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 覆盖正确率 | 本轮提及的槽位被正确更新 | — |
| **保持率** | 本轮**未**提及的槽位保持不变 | **100%**（硬性） |
| 清空正确率 | 用户显式否定时槽位被置空 | — |

**保持率是硬性 100%**：用户说"第三天换一下"，结果出发地变了，这是不可接受的。

### 3.3 澄清决策

| 指标 | 定义 |
| --- | --- |
| 追问必要性判定 | 该追问时追问、不该追问时直接生成的准确率 |
| 追问有效率 | 追问的问题确实是阻塞项的比例 |
| 平均追问轮次 | 越少越好（但不得以"从不追问"换低分） |
| 追问冗余率 | 追问了上下文中已存在的信息的比例（目标 0） |

**必须成对看待**：只优化"平均轮次"会催生"从不追问"的退化策略；只优化"完整性"会催生问卷式追问。因此两个指标必须同时报告。

### 3.4 工具参数正确性

工具调用是**确定性可验证**的环节，应当优先做：

| 指标 | 定义 |
| --- | --- |
| 工具选择准确率 | 选对了工具 |
| 参数准确率 | 逐参数比对期望值 |
| 参数幻觉率 | 生成了工具 schema 中不存在的参数（目标 0） |
| 不必要调用率 | 调用工具获取了上下文中已有的信息 |
| 超时/重试行为 | 重试次数是否 ≤ 上限；不可重试错误是否未重试 |

### 3.5 行程约束满足率

**全部为确定性校验，不需要 LLM 判定。**

| 约束 | 校验方式 |
| --- | --- |
| 天数正确 | `len(days) == duration_days` |
| 预算不超 | `sum(costs) <= budget`（口径需一致） |
| 必去景点包含 | 景点集合包含关系 |
| 节奏匹配 | `relaxed` 日安排时长 ≤ 阈值 |
| 兴趣覆盖 | 相关类别条目占比 ≥ 阈值 |
| 时间不重叠 | 同一天条目区间无交集 |
| 通勤可行 | 相邻条目间隔 ≥ 估算通勤时间 |
| **无编造事实** | 每个事实字段都能在工具返回中找到对应值 |

**「无编造事实」是硬性指标，目标恒为 0 违规。** 实现方式：在评测环境中记录全部工具返回，逐字段反查行程中的事实性内容是否能在工具结果中找到来源。

### 3.6 执行恢复正确性

| 场景 | 期望 |
| --- | --- |
| 中断后恢复 | 从上次节点继续，不重复已完成的有副作用操作 |
| Checkpoint 缺失 | 仅凭业务数据重建上下文，功能降级但不报错 |
| 重放幂等 | 同一请求重放两次，业务数据只产生一份结果 |
| 并发修改 | 版本号不匹配的写入被拒绝 |
| 状态一致性 | 恢复后的 `TripRequest` 与中断前一致 |

**这组指标在实现 Checkpoint 之前无法测量**，但用例可以先行编写。

### 3.7 任务成功率、Token 与延迟

| 指标 | 定义 |
| --- | --- |
| 任务成功率 | 无需人工干预、产出通过全部硬性校验的行程的比例 |
| 澄清后成功率 | 分母限定为"经过至少一轮澄清"的会话 |
| Token 消耗 | 按输入 / 输出 / 缓存命中分别统计，报告 P50 与 P95 |
| 单次行程成本 | Token × 单价，按模型分别统计 |
| 延迟 P50 / P95 | 端到端；并按节点拆分，定位瓶颈 |
| 轮次分布 | 完成一次规划所需的对话轮数 |

**Token 与延迟必须与成功率同时报告。** 单独看任何一个都能被轻易操纵（牺牲质量换速度、或反之）。

## 4. 数据集格式

定义于 [`evals/cases.jsonl`](../../evals/cases.jsonl)，一行一个 JSON 对象。

```jsonc
{
  "id": "slot-extraction-001",        // 全局唯一，稳定不变（指标趋势依赖它）
  "category": "slot_extraction",      // 见下表
  "description": "从完整自然语言中提取全部槽位",
  "input": {
    "message": "我准备周五晚上从深圳出发，在长沙玩三天，预算 2000 元，喜欢美食和人文景点，不想每天安排得太满",
    "prior_state": null,              // null 表示首轮；否则是已积累的 TripRequest
    "tool_fixtures": null             // 指定工具返回的确定性数据；null 表示用默认 fixture
  },
  "expected": { /* 该类别对应的期望结果 */ },
  "assertions": [ /* 机器可判定的断言列表 */ ],
  "tags": ["zh", "relative-date"]
}
```

### 类别

| `category` | 评测内容 | 对应指标 |
| --- | --- | --- |
| `intent` | 意图分类 | 3.1 |
| `slot_extraction` | 从零提取槽位 | 3.2 |
| `slot_update` | 增量更新与保持 | 3.2 |
| `clarification` | 是否追问、追问什么 | 3.3 |
| `tool_call` | 工具选择与参数 | 3.4 |
| `planning` | 行程约束满足 | 3.5 |
| `resume` | 恢复与幂等 | 3.6 |
| `safety` | 不编造、不越界 | 3.5 |

### 断言类型

```jsonc
{ "type": "field_equals",  "path": "destination", "value": "长沙" }
{ "type": "field_is_null", "path": "budget" }
{ "type": "collection_equals", "path": "interests", "value": ["food", "culture"] }
{ "type": "collection_contains_all", "path": "missing_slots", "value": ["start_date"] }
{ "type": "tool_called", "tool": "poi_search", "args_contain": { "city": "长沙" } }
{ "type": "tool_not_called", "tool": "weather_forecast" }
{ "type": "constraint_satisfied", "constraint": "budget_within_limit" }
{ "type": "no_fabricated_facts" }
```

断言用**声明式数据**而非代码，这样评测集可以被非工程师扩充，也能被不同实现复用。

### 数据来源（按优先级）

1. **手工构造的边界用例**——歧义、冲突、缺失。覆盖率最高，成本最高。
2. **真实用户输入**（脱敏后）——分布最真实。需用户授权。
3. **对已有用例做扰动**——同义改写、口语化、加入错别字，用于测试鲁棒性。

**当前 `cases.jsonl` 中只有第 1 类，且仅作为格式样例。**

## 5. 判定方法

| 方法 | 适用 | 风险 |
| --- | --- | --- |
| **规则判定** | 槽位、工具参数、约束满足（3.2 / 3.4 / 3.5 / 3.6） | 几乎无风险，优先使用 |
| **集合比对** | 兴趣、必去景点 | 需定义顺序与重复的语义 |
| **LLM-as-judge** | 行程合理性、解释质量、语气 | **有风险**，见下 |
| **人工抽检** | 校准 LLM 判定器 | 成本高，但不可省 |

### LLM-as-judge 的使用纪律

1. **能规则判定的绝不用 LLM 判定。** 3.2 / 3.4 / 3.5 / 3.6 全部可规则化。
2. LLM 判定器必须**与生成模型不同**，否则会偏袒同源输出。
3. 判定器需**先用人工标注的样本校准**，报告与人工的一致性。
4. 判定器必须**给出理由**，并对"不确定"显式返回，而不是强行二选一。
5. 判定器的提示词变更等同于评测标准变更，**必须记录版本**。

## 6. 基线与回归流程

```
1. 冻结评测集版本（cases.jsonl 的 git commit）
        │
2. 跑当前实现，得到指标快照
        │
3. 将快照标记为基线
        │
4. 每次变更（提示词 / 模型 / 工具 / 工作流）后重跑
        │
5. 与基线逐指标对比
        │
   ┌────┴────┐
   v         v
 改善      退化 → 定位到具体失败用例 → 决定接受还是回滚
```

**要求**：

- 评测集版本与实现版本**必须一并记录**，否则指标不可比。
- 报告**失败用例清单**，而不只是聚合指标。聚合数字会掩盖"某类输入全错"。
- 引入真实 LLM 后，报告需注明模型名称与版本——模型换代会让指标失去可比性。

## 8. 尚未定义的部分

以下问题**尚未有答案**，将在对应阶段确定。列出以免被误认为已解决：

1. **阈值的确定方式**：多高的槽位 F1 算"可以发布"？需要先有基线才能谈。

## 9. 明确声明

**本文档不含任何准确率、成功率、覆盖率或性能数值。**

原因是：这些能力尚未实现，任何数字都只能是编造的。评测方案的价值在于**先把判定标准定义清楚**，这样实现完成时可以直接测量，而不是事后补一套标准来迁就已有结果。
